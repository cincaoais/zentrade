# Builder check — Chan + Wyckoff harness

Read the design, the four `s3-*` notes, and the cited code. Ranked; only guesses that would change the build.

1. **Random-entry baseline: what is "same exits"?** A random entry has no Chan/Wyckoff point, so no `invalidation_price` for exit (a) or for R. Does B0-rand use (i) the variant's exit rows for the same symbol, (ii) only `max_hold` + `−15%`, or (iii) a synthetic invalidation (e.g. entry × 0.95)? Also, does "same count per day" mean emitted entries or filled trades after `max_positions=10`? Why: the 95th-percentile gate compares CAGR, so a different exit/stop/capacity policy changes the percentile and the gate can pass/fail on baseline construction rather than signal skill.

2. **What counts as a trial for DSR?** Does N include variants tried only on development, the 8 follow-ups if tried, and holdout re-runs after a bug/data fix, or only the 16 holdout runs? Are the 200 random seeds excluded (doc says baselines do not count)? Why: `DSR ≥ 0.9` is sensitive to N; if only survivors enter N, the gate under-corrects for selection and can be meaningless. N must be fixed at freeze, not after.

3. **R's denominator, and Wyckoff invalidation.** `R = (exit−entry)/(entry−invalidation)` is undefined/negative if the t+1 open is at/below invalidation (a gap; 1B invalidation is the point price, `engine.py:170`; 2B uses the 1B low, `:193`; 3B uses `zg`, `:214`). Rule: skip the entry, exit immediately, floor the denominator, or use ATR? Also H2 includes `sos`, whose `wyk` Event has no `stop_ref` (`accumulation.py:425-440`; only `entry_steady`/`lps` carry one, `:346-347,523`). What invalidation does H2 use for SOS and for any event without one? Why: "average R > 0" is a pass condition, and one tiny denominator can make it pass on a single lucky trade.

4. **How are B0-bh and B0-spy run?** "Equal-weight buy-and-hold of universe members at period start, held to period end" cannot run under `max_positions=10`; is it a separate calculation or a special ZenTrade run? Does it pay the same commissions/slippage/fills? Which universe snapshot (holdout start or dev start) and weighting, and what happens to names that leave the universe? Why: "CAGR > B0-bh" is the primary gate; a fully invested 1,500-name benchmark vs a 10-name variant with cash drag is not a like-for-like edge test.

5. **Where is the point-in-time universe filter applied?** The replay runs on the union, and Chan replay starts at bar 120 while eligibility needs 250 bars, $5 and $10M (top 1,500). Are entry rows intersected with the eligible set at each t in `compose.py`, and does the bridge refuse non-eligible entries? Are exits allowed after a held name drops out? Why: if only the replay is filtered, the variant trades names outside the stated universe and the random/benchmark comparison is on a different universe.

6. **Phantom rate is not computable as defined.** The engine reports only points in the last 9 strokes (`engine.py:45,557-561`) and the point dict has no stroke index (`engine.py:445-468`). "Absent from a later snapshot" therefore includes normal window exit, so the rate would be near 100% and not a repaint measure; a point can also reappear if a stroke is removed. What is the precise definition, and what extra column (stroke index / last-reported date / window-end date) must the replay record? Why: this is one of the three integrity checks.

7. **How is the exit table made path-independent?** Exit (a) needs the invalidation of the entry actually filled, and (b) "sell point known while holding" depends on holdings; `max_positions=10`, cash, and any re-entry decide which entries exist. Does the composer (i) simulate the matcher (and then it must match ZenTrade), or (ii) emit exits for all signal days and let the engine apply them when flat/held? Is re-entry into the same symbol allowed? Why: affects trade count, average R, and whether the composed table can be precomputed at all.

8. **What does freeze/evaluate pin?** The table is cached by `engine_version` only (vendored file hash + czsc version), and the registry records id/params/code hash/date. Does freeze/evaluate also verify the data snapshot hash, universe version, replay start bar, composed-table hash and the bridge strategy code? The constraint says "6,342 stocks once the backfill finishes", so the store may still be moving. Why: otherwise a data refresh or a post-freeze edit silently changes holdout results and the lock is ceremonial.

9. **First-seen = candidate, and there is no confirmed-date row.** The newest finished stroke is labelled `candidate` and "may still be redrawn or removed" (`engine.py:404-415`), so every first-seen Chan entry is a candidate; the table stores `state_at_known` but no confirmation date. Is entering on candidates intended, or must the replay also emit a state-transition/confirmed-date row so a "confirmed-only" variant can be built? Why: this is the core repaint exposure, and the current schema rules out the obvious robustness variant.

10. **Survivorship vs the anti-goal.** The doc lists "today's stock list applied to past dates" as an anti-goal but also accepts survivorship as a reported non-goal. Which reading governs? If the survivor-only moomoo list is the accepted exception, must B0-bh and B0-rand use the same survivor universe so the bias is shared? Why: determines whether the harness is compliant and how every comparative number must be caveated.

11. **Which sell points exit which entries?** "A same-level sell point (Chan)" is ambiguous: any of 1S/2S/3S at the daily level, or only the matching number (1B→1S, 2B→2S, 3B→3S)? Do Chan sell points also exit Wyckoff entries (H2/H3), and do SOW/UTAD exit Chan entries? Why: changes exits, R and trade counts.

## Claims contradicted or incomplete vs cited code

- **Dollar volume.** The Inputs say "split-adjusted volume", but the universe uses `raw close × volume`. `volume` is multiplied by the split factor (`backend/app/indicators/pipeline.py:282-286`), `raw_close` is unadjusted (`pipeline.py:107-110`), and `amount` is deliberately unadjusted (`pipeline.py:283`) and USD (`backend/app/api/monitor_rules.py:93`). Pre-split dollar volume is overstated by the split factor; worse, that factor is future information at t, so the rule also violates the doc's own anti-goal. Use `amount` (or reconstruct raw volume).
- **Phantom rate.** `engine.py:45,557-561` reports only the last 9 strokes; the point dict (`engine.py:445-468`) has no stroke index, so the doc's "absent from a later snapshot" cannot separate window exit from repaint.
- **H2 invalidation.** The entry-row schema assumes an invalidation, but `wyk` `sos` has no `stop_ref` (`accumulation.py:425-440`); only `entry_steady` (`:346-347`) and `lps` (`:523`) do.
- **Data claim.** The 1,000-day / 6,342-symbol figures cite a step-2 dry run/backfill log that is not in the cited notes; `data/kline_daily_enriched` is empty in this checkout, so I could not verify them.
